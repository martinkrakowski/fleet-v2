# Wire the Nitro API

*Date: 2026-10-13 · Status: draft, not adopted · Owner decision: pending*

`apps/api` is a composition root (`docs/architecture.md`). Today `nitro.config.ts` sets `srcDir: "server"`, and the only route is `server/routes/index.ts`: `GET /` returns `{ status: "ok", app: "api" }`. The four context packages are already dependencies. Every inbound port is an empty interface, and every use case throws `Not implemented`. The lanes running on 2026-10-13 do not add routes. This plan is the route surface those ports need. It does not start a lane.

## Rules

- A route calls one use case. It does not call `ocm-run`, Waves, the shelf, git, or a host script.
- The composition root (`server/composition.ts`) constructs use cases and the adapters they need. Routes receive that object. They do not construct a package themselves.
- Request and response bodies use the port types from migration step 1. Until those types exist, a route accepts no body and returns 501.
- `Not implemented` is HTTP 501 with a stable `code`. An unknown attempt outcome is HTTP 409, not 200. A missing attempt is 404. A body that fails the port type is 400.
- No secret, token, key, or `.pgpass` in a request, a response, or a log line. The runner endpoint comes from `installation/` inside the adapter, never from the client.
- `GET /` stays the process check. It does not claim a station is implemented.
- Forge, a new Waves contract, and a view owner stay closed until the owner decides those doors (migration step 7, W1, W2). The routes exist and return 501.

## Envelope

Every JSON body except `GET /` uses:

```text
{ "operationId": string, "code": string, "result": object | null }
```

`operationId` is the server's id for that call. A client retry of the same operation sends `Idempotency-Key`. The journal (migration step 3) is what makes that key durable. Before step 3, a repeated key on a still-open call returns 409 and does not dispatch again. There is no auth platform in this scaffold. The dev server stays on port 3001. Binding it beyond loopback is an installation choice, not a default.

## Steps

| # | Step | Who | Verification |
|---|---|---|---|
| A | Add the composition root, the error envelope, and one route file per row above. Each handler calls its use case and maps the thrown `Not implemented` error to 501. `GET /` unchanged. | one fleet-v2 lane, after step 1's types compile, or sooner if every body stays empty | `yarn typecheck` in `apps/api`. A request to each new path returns 501. `GET /` still returns ok. |
| B | Replace empty bodies with the step 1 port types. Reject a body that does not match. | one lane | A bad body is 400. A valid body against an unimplemented use case is still 501. |
| C | As each migration step lands, that step's routes return its real result. Do not enable a later row early. | the lane that owns that migration step, in this app only | The table's "Returns 200 only after" column. |

Steps A and B are one lane each. They do not run beside a lane that is editing the same port files. The doc lanes do not conflict with them.

## What this plan does not do

- It does not choose W2 (who draws the five views). `apps/web` keeps calling this API later.
- It does not add a Waves contract type (W1) or store a token.
- It does not onboard a container, set a key, or deploy.
- It does not add auth, a database, or a public bind.

## Risks and rollback

- A route that shells out would bypass the use case and can touch midnight. Review A by checking that `server/` does not import `node:child_process`.
- Enabling `POST /v1/attempts` before the step 3 journal can double-dispatch. The table keeps that route dark until step 2, and the idempotency key is not durable until step 3.
- Rollback is reverting the `apps/api` commit. The CLI is unaffected.
