# Adding a host: single machine to multi machine, and back

*Date: 2026-10-17 · Status: revision 3.2 (owner: "Update the plan to close all gaps"; section 7 lifts the
one-lane-runner limit and section 8 removes the shared-storage assumption), previously 2.1, after Grok and Fable (both not ready on revision 1; every blocker
answered below) · Builds on `2026-10-16_onboarding-and-init.md` (schema v2, executors, `init`, `doctor`,
Amendment O14) and `2026-10-16_onboarding-settings-ui.md`. Owner request: "allow a developer to add a
secondary host like midnight.lan when onboarding and configuring the project. It should be able to run on a
single host or multiple hosts like we are currently running. This should be easily configurable."*

## Goal

A developer starts on one machine and later moves lanes to a second host (such as midnight.lan), adds a
verifier host, or removes them again, with one short command or one Settings card. The installation file is
the only source of where things run; no environment variable can silently redirect a lane.

## Non-goals

- A resident agent on remote hosts (section 9 explains why bootstrap over ssh replaces it).
- Starting a lane during onboarding. Probes never start a lane or open a lasting tunnel.

## What exists, and the gaps (verified)

- Schema v2 describes hosts (`transport`, `sshAlias`, `worktreeRoot`, `tmpDir`, `roles`, `runner`), and the
  loader already applies environment overrides only to v1 or absent files (`packages/installation/src/load.ts`).
  Executors pick local or ssh from `transport`; the orchestrator executor is always local
  (`ExecutorSelector.adapter.ts`).
- **Gap 1: no way to add or remove a host after `init`** except hand-editing JSON.
- **Gap 2: environment variables still win in the roots and adapters**, even with a v2 file:
  - `resolveRunnerSettings` (apps/cli/src/composition.ts) and the API's `resolveWorkRunnerSettings`
    (apps/api/server/wiring/work/composition.ts) read `OCM_REMOTE_PORT`, `OCM_HOST`,
    `FLEET_WORKTREE_SSH_HOST` and `FLEET_OCM_RUN_BIN` whenever the v1 fields are absent, which is always for v2;
  - the resolved `worktreeSshHost` is passed to `resolveRoleExecutors` as an override that beats the v2
    hosts, so a stale `FLEET_WORKTREE_SSH_HOST` already redirects the worktree executor, `readGitHead` and the
    forge push;
  - `ExecutionRunnerAdapter` falls back to `process.env` for its port and host, and its runner environment
    allow-list forwards inherited `OCM_REMOTE_PORT` and `OCM_HOST` to `ocm-run`;
  - `OcmReviewTransport` reads `OCM_HOST` from the environment (not wired yet; the same rule applies);
  - `bin/ocm-run` defaults a missing port to 4096;
  - `runner.authFile` is never used at dispatch: `ocm-run` reads `OPENCODE_AUTH_FILE`, which nothing sets.
- **Gap 3: ports.** `bin/ocm-run` always dials `127.0.0.1:<port+1>` and, when that is not listening and
  `OCM_HOST` is set, opens `ssh -f -N` to `<port>` on the host. For a local host nothing documents that the
  developer must serve on `port+1`; `installation.example/single-machine/fleet.json` (`port: 46000`) only works
  with `opencode serve --port 46001`.
- **Gap 4 (closed by section 7): the runtime addresses one lane-runner host.** The capability profile and the `RunnerSelector` take
  the first `lane-runner` host; `ExecutionRunnerAdapter` holds one port and host; reconcile and stop refuse an
  attempt recorded on another host; `maxLanes` is one number.

## Design

### 1. Hosts are the configuration; three rules in the loader

- **Lane-runner hosts.** Until H9a lands the loader allows exactly one lane-runner host (H1, a temporary rule
  matching today's runtime). H9a lifts it: then any number of lane-runner hosts, each with its own runner kind,
  port and `maxLanes`. `hosts add --role lane-runner` asks "also run lanes here, or move lanes here?" only
  after H9a; before it, adding one moves the role. This matches what the runtime can address
  and keeps the story simple: "lanes now run on midnight; this machine keeps orchestrator and verifier".
- **The orchestrator host's transport must be `local`** (the runtime already forces a local executor). The
  committed `installation.example/multi-machine/fleet.json` and the O2 tests change to match.
- **`runner.port` is the server's port on its own host.** No `tunnel` field. The port the orchestrator
  actually dials is derived: `port` for a `local` host, `port + 1` (the forward) for an `ssh` host. **The
  derived dial ports must be unique across hosts**; that is the whole collision rule (a local host on 46001
  and an ssh host on 46000 collide and are refused).
- `runner.authFile` is a path **on the orchestrator** (where `ocm-run` runs). `ocm-run` sources it as shell, so
  doctor and the probe require it to be owned by the orchestrator user, a regular file, and neither group- nor
  world-writable (mode 600 recommended).
- Every write (add, edit, remove, Settings) goes through the loader; `--force` never bypasses a loader rule.

### 2. Local and remote ports behave the same (H0)

`bin/ocm-run` changes so a local host is dialled at `port` directly when `OCM_HOST` is empty (no tunnel),
and a remote host keeps the `port + 1` forward. The missing-port default of 4096 is removed: no port, no
dispatch (exit 2). `--check` becomes read-only: it never opens a forward, it only reports whether the dial
port is listening and whether the configured host's forward is the one holding it; a forward is opened only
by a real dispatch. The single-machine example then means what it says. This is a hash-pinned script, so H0
updates `tests/ocm-run.test.sh` and `scripts/ocm-run-hash.txt` and is reviewed by Fable.

### 3. Runtime reads the selected host, never the environment

With a v2 installation:

- the runner's kind, ssh alias, port and worktree root come from the single lane-runner host (the
  `RunnerSelector` and the capability profile read that one host, not "the first" of several); the worktree executor uses
  that host; the verifier executor uses the verifier host (none: local, and `hosts edit` says so);
- `ExecutionRunnerAdapter` sets `OCM_HOST`, `OCM_REMOTE_PORT` and `OPENCODE_AUTH_FILE` itself from the
  selected host and **removes `OCM_HOST` and `OCM_REMOTE_PORT` from the inherited allow-list** (narrowing is
  allowed by AGENTS.md); with no port it refuses;
- `resolveRunnerSettings` and `resolveWorkRunnerSettings` stop reading `OCM_*`, `FLEET_WORKTREE_SSH_HOST`
  and the `worktreeSshHost` override for v2; `FLEET_OCM_RUN_BIN` stays (a binary path, not a route);
  `FLEET_RUNNER_AGENT|MODEL|VARIANT` are replaced by v2 seats and ignored for v2;
- `OcmReviewTransport` follows the same rule when it is wired;
- **reservations and attempts record the installation host name** (`hostId` from the selection), so a
  host's running work can be found;
- v1 and absent installations keep today's environment behaviour unchanged;
- a parity test runs both roots on the same v2 file with every variable set and asserts identical resolved
  settings with the environment ignored;
- `doctor` prints a FAIL line naming (never valuing) each routing variable set while a v2 file is loaded.
  No deprecation period: a warning that still lets the variable win would be the one silent redirect left.

### 4. `fleet-v2 hosts` (small surface)

```
fleet-v2 hosts list
fleet-v2 hosts add <name> --ssh <alias>      # prompts for worktree root, role (default lane-runner), port
fleet-v2 hosts edit <name>                   # roles, port, worktree root
fleet-v2 hosts remove <name>
fleet-v2 doctor --host <name>                # the check, no separate command
```

- **add** = draft → probe → write.
  - *Draft:* the alias must pass the existing `isSafeSshHost` rule; flags or prompts fill the rest; a v1 file
    is converted to v2 on this first write and the isolation step is forced (the same rule as the Settings
    plan), so a converted runner is never silently `undeclared`.
  - *Probe:* the host's subset of `doctor`, all argv arrays with `BatchMode=yes`, `ConnectTimeout` and `--`:
    reachability; `sh`, `git`, `node` and the runner tool with versions; worktree root writable (`mktemp -p
    <worktreeRoot>` then `rm` of exactly that path, never a shell string); the opencode server answering **on
    the host's own loopback through ssh** (`ssh <alias> -- curl -fsS --max-time 5 http://127.0.0.1:<port>/…`),
    never through a local forward, so no tunnel is left open and no other host's server can answer;
    capability declaration and its `source`; the orchestrator-side auth file mode. A verifier host also checks
    that it can see the lane-runner's worktree root (`test -d`), the assumption verification relies on.
  - *Write:* compare-and-swap with the same file-hash scheme as the Settings plan (`expectedHash`), showing the
    diff, after confirmation or `--yes`.
  - **Exit codes:** 0 written, 1 refused (any probe FAIL or loader refusal), 2 usage. UNKNOWN lines are shown
    and do not refuse. There is no `--force`.
- **edit** follows the same steps; moving the lane-runner role prints the one-sentence summary.
- **remove** refuses the orchestrator host and the last lane-runner, and refuses while the host has live work:
  any attempt recorded on that host whose state is not in work-execution's `CAPACITY_RELEASE_STATES`
  (ended, collected, cancelled; the same constant, not a hand-written list), or any active reservation with
  that `hostId` (`listActiveReservations(hostId)`; H3a makes `hostId` the installation host name). It prints
  how to close a leftover `ssh -f -N` forward on `<port+1>`. Removing the last ssh host returns the install
  to single machine.
- `doctor --host <name>` also reports a listening forward on a port no configured host owns.

### 5. One engine for every surface

The draft, validation, probe plan, diff and compare-and-swap write are the **shared onboarding engine** the
Settings plan (S2, U0) assigns to `@fleet/onboarding`. H2 builds it and O10 (`init`) and the Settings write
path consume it, so `hosts add`, `init`'s multi-machine step and the Settings **Hosts** card produce
byte-identical files. Doctor's probes gain a per-host worktree root (today they test one path).

### 7. Several lane-runner hosts at once (closes gap 4)

**The host is chosen when capacity is reserved, before anything exists on a host.** `fleet-v2 work reserve`
(and its API route) no longer takes an operator-typed `hostId`. Inside the journal's locked
read-modify-write, the reserve use case receives the installation's lane-runner hosts with their `maxLanes`
(default 1), the seat's tool (from the request's chain seat, not the frozen brief), and the brief's isolation
requirements; it keeps the hosts whose runner kind equals the tool and whose declared isolation meets the
requirements, counts held reservations per host under the same lock, picks the host with the most free slots
(ties by name) and records the claim. If that host is full by the time of the claim it tries the next eligible
host; none free gives `no-capacity` (exit 1). A blank or unknown seat tool, or a kind with no runner adapter
(agy until O14e1), refuses; the selector never defaults to opencode. An optional `--host <name>` belongs to
**reserve**, not dispatch (dispatch keeps refusing host fields), and is still checked against the same rules.

The reservation records the host's **name, kind, transport, ssh alias and port**, and the **worktree path**
is allocated inside the same lock: `<host worktreeRoot>/<digest>` where `<digest>` is the first 32 hex of sha256
of the attempt id, so no caller text reaches a path. The busy-worktree check runs on (host, path) under that
lock, so two claims on one host can never prepare the same tree. Brief preparation, the
worktree and dispatch then run on that host, and dispatch refuses when the reservation's host does not own the
attempt's worktree.

**After dispatch, the recorded host is the truth.** Inspect, reconcile, stop, collect, workspace and artifact
reads, `readGitHead` and the forge push are built from the host recorded on the attempt. The current
installation is consulted only to confirm: if the host with that name now has a different kind, transport,
alias or port, the action returns `unknown` (inspect) or refuses (stop, collect, push) and names the recorded
host; a renamed or removed host behaves the same. The orchestrator's `existsSync(worktreePath)` heuristic for
local-versus-remote git reads is replaced by the recorded transport.

**Compatibility.** v1 and absent installations keep one legacy runner adapter built from today's environment,
with `hostName: null`. Attempts recorded before H9a (no host name; `runner.host` holds the alias) are read with
the legacy rule: the recorded alias and port must equal the single lane-runner's, else `unknown`.

`CAPACITY_RELEASE_STATES` is exported once from work-execution (the duplicate in `Attempt.ts` removed) and used
by `hosts remove`. Doctor and `hosts list` show each lane-runner's held and free slots; the Settings Hosts card
reads them through `GET /v1/settings` (U7).

### 8. Verification without shared storage

A separate verifier never fetches from the lane-runner itself, so it needs no credential for it and no agent
forwarding is ever used. The **orchestrator** moves the commit, as it already does for the forge push:

1. `git fetch <lane alias>:<worktree> <full sha>` into the orchestrator's repository (argv only, the strict
   `isSafeSshHost` rule from `WorkspaceAdapter`, `GIT_SSH_COMMAND` with `BatchMode=yes` and a connect timeout).
2. `git push <verifier alias>:<verifier worktreeRoot>/.verify/<digest>.git <full sha>:refs/verify/<digest>`,
   where `<digest>` is the first 32 hex of sha256 of the attempt id and request id, so no caller text reaches
   a path.
3. On the verifier (argv over ssh): `mktemp -d <worktreeRoot>/.verify/run.XXXXXX`, refuse unless the resolved
   path is under `.verify`, `git clone --no-checkout` from the bare repo, `git checkout --detach <full sha>`,
   assert `git rev-parse HEAD` equals the bound full sha, run **every** procedure of the request there, then
   remove exactly that path and the bare repo, also on failure.
4. Procedures receive the checkout path as an explicit trailing argument (after the sha); the same-host case
   uses the same scratch flow, never the live worktree.

Full 40-hex shas are required for this path. The verifier probe checks git on both hosts and that the
orchestrator can push to the verifier. Verification requests carry the lane host name and worktree path read
from the attempt record; the verifier's `hostId` comes from the installation, not the operator.

### 9. Provisioning: bootstrap over ssh (owner question, 2026-10-17)

Instead of a resident agent (a remote command channel, a server on the laptop, and its own security stack),
**`fleet-v2 hosts bootstrap <alias>`** copies a pinned, hash-checked script over ssh and runs it as the
developer's own user after showing exactly what it will do. Hardening:

- ssh only as argv, through the strict `isSafeSshHost` rule, `BatchMode=yes` and a connect timeout; the alias is
  never interpolated into a shell string on either side.
- The script refuses to run as root (`id -u` = 0) and never calls `sudo`.
- Nothing is downloaded at "latest": node and opencode versions are pinned in the script with SHA-256 checksums
  verified before anything runs; a mismatch stops. A developer may instead require both to be preinstalled
  (`--no-install`), and the script then only checks versions.
- The opencode auth file is generated on the remote host from its own random source, written with mode 600,
  and its contents are never printed, returned or put in the descriptor; the descriptor holds only its path,
  and the orchestrator-side auth file the developer creates separately (doctor checks it).
- The optional lane container is referenced by image digest, runs rootless, without `--privileged`, with only
  the worktree root mounted and network egress limited as declared.
- The transcript shows commands and outcomes, never file contents.

Behaviour: It is idempotent and only does what is
missing: checks or installs node and opencode in user space, creates the worktree root, writes the opencode auth
file (mode 600), starts `opencode serve` on the chosen port as a user service, optionally starts the published
lane container instead, and prints a **host descriptor** (JSON: tools and versions, port, worktree root,
declared capabilities). **`fleet-v2 hosts add <name> --from-descriptor <file>`** reads an allow-listed set of fields
(tool names and versions, port, worktree root, capability booleans and scope); any other field, including a
capability `source`, is refused; the loader still derives `source`, and the usual probe runs and overrides
anything it can measure before the write. Cross-network reachability is left to the developer's network (a mesh VPN such as Tailscale
makes `ssh <name>` work behind NAT with no inbound service on the laptop); fleet-v2 only uses the ssh alias.
Running the bootstrap is host administration and needs the developer's explicit command each time.

## Hard to undo

- Ignoring routing environment variables for v2 installs changes behaviour for anyone exporting them today
  (the owner); `doctor` names each one.
- Removing `ocm-run`'s 4096 default and dialling local hosts directly changes the hash-pinned script.
- Per-host capacity changes how the journal counts slots; `maxLanes` per host replaces one global `maxSlots`.
- Attempt records gain host name, kind, alias and port; after-dispatch actions follow the recorded host.

## Assumptions

- Hosts are reachable non-interactively through the developer's ssh config by alias.
- A separate verifier needs no access to the lane-runner: the orchestrator relays the commit (section 8).
- The opencode server exposes an unauthenticated health path on its loopback; if not, the probe falls back
  to a TCP check and says UNKNOWN for identity.

## Challenge this

Choosing the host with the most free slots is simple and predictable but ignores host speed; a slow and a
fast box get lanes evenly. Weighting is easy to add later; picking by free slots keeps the selector pure and
testable.
