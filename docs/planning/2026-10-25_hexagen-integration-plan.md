# Plan: fleet-v2 and hexagen as one pipeline, without coupling

- **Date:** 2026-10-25
- **Target repository:** `fleet-v2` (lanes F1–F7). The hexagen side (H1–H4) is a separate plan in `hexagen-monaco`, owned there.
- **Status:** the owner accepted the recommendations on 2026-10-25 ("Please proceed with your recommendations"). Nothing is built yet.
- **Owner request (2026-10-25):** combine hexagen-monaco and fleet-v2 "as a cohesive pipeline without marrying the two projects".
- **Owner decisions (2026-10-25):**
  - **Contract ownership** resides with hexagen-monaco.
  - **Contract changes** most likely start from a fleet-v2 need. They become a work order against hexagen-monaco, and a release fans out update work orders to every provisioned project that depends on the contract, fleet-v2 included.
  - **Detection:** a hexagen-generated project is identified simply at provisioning, from `.architecture/manifest.yaml`.
- **Source:** a read-only investigation of both repositories (Fable, 2026-10-25). Citations are to paths on each `main`.

## 1. Where the two projects stand (checked 2026-10-25)

- **fleet-v2 uses hexagen only as pinned dev tooling:**
  - `@hexagen-monaco/sync` and `@hexagen-monaco/arch-linter` at exactly `0.14.0` (`package.json` devDependencies);
  - the root scripts `sync`, `sync:check` and `lint:arch`, which CI runs on every pull request (`.github/workflows/gate.yml`);
  - `.architecture/manifest.yaml` (`schemaVersion: 1`, `generator.version: "0.14.0"`);
  - barrels stamped `// @generated by @hexagen/sync`.

  No fleet-v2 source imports `@hexagen-monaco/*`, and no port or adapter wraps hexagen.
- **hexagen has no code that refers to fleet-v2.**
- **Three spots are already coupled:**
  1. The toolchain pin and script names sit inside a hexagen-owned root template in fleet-v2's manifest, so an upgrade means re-syncing that template.
  2. `hexagen arch validate`, the `lint:arch` gate, gives only a human-readable pass/fail. It uses exit 1 both for "violations" and for "could not run".
  3. fleet-v2 was first generated from a hexagen working copy (`docs/scaffold-verification.md`). It now uses the published package.
- **hexagen's declared contract** (its ADR-0056) is its command-line tools: commands, flags, exit codes and effects on disk. Already machine-readable:
  - `hexagen-lint --json`, with exit codes 0 (compliant), 1 (violations) and 2 (could not run);
  - `hexagen sync --check`, exit 0 or 1;
  - a versioned manifest (`schemaVersion`, plus `hexagen manifest migrate`).

### 1.1 The two lint commands, and which lane uses which (checked against hexagen `main`, 2026-10-25)

| Command | Package (pinned 0.14.0) | What it does | Output | Exit codes |
|---|---|---|---|---|
| `hexagen arch validate`, which is fleet-v2's `yarn lint:arch` and what CI runs | `@hexagen-monaco/sync` (bin `hexagen`) | Validates the manifest, then runs the arch-linter internally and hides its output | One human-readable line | 0 compliant; 1 for both violations and "could not run" (until hexagen's H2) |
| `hexagen-lint --json` | `@hexagen-monaco/arch-linter` (bin `hexagen-lint`) | The arch-linter alone, without manifest validation | One JSON line: `fresh`, `baselined`, `stale`, `expired`, `introduced`, `baselineGrowth`, `filesScanned` | 0 compliant, 1 violations, 2 could not run |

They are separate commands, not aliases. **The mapping this plan uses:**
- **The merge gate stays `lint:arch`** (`hexagen arch validate`), the same command CI runs.
- **`hexagen-lint --json` is used only where machine-readable findings are needed** (F4 evidence), alongside the gate, never instead of it.
- **Once hexagen's H2 ships `arch validate --json`** with exit 2, F4 switches to it, and one command serves both purposes.

## 2. The rules that keep the projects separate

1. **They meet only at hexagen's published contract:** its command-line tools, their JSON output and exit codes, and the manifest format. fleet-v2 never imports hexagen code, never adds it as a runtime dependency of any `apps/*`, and never names it in its domain or application layers. hexagen is reached only through an infrastructure adapter behind a port.
2. **hexagen-monaco owns the contract.** fleet-v2 keeps its own lenient copy of the shapes it reads, which ignores unknown fields. It never patches the contract on its own side.
3. **Changes flow as work orders** (owner, 2026-10-25):
   1. A fleet-v2 need becomes a work order against the hexagen-monaco project, gated by hexagen's own CI.
   2. hexagen releases a version: additive in a minor, or breaking with a migration path.
   3. fleet-v2 detects the release and proposes **one update work order per provisioned project that depends on it, fleet-v2 included**.
   4. Each update bumps the pin, runs `hexagen sync`, then `sync:check` and `lint:arch`, and merges on that project's own CI and the owner's approval.

   fleet-v2 never auto-merges a contract bump across projects. One failing project blocks no other.
4. **The loop breaker:** fleet-v2 uses only a **published, exactly pinned** hexagen release, never a working copy, worktree, branch or lane output. Its own update is one fan-out work order among the rest, and its running orchestrator keeps the old pin until that pull request merges.
5. **Mixed versions are normal.** Projects upgrade at different times, so the adapter handles every hexagen version still in the inventory.
6. **Missing hexagen is never a pass.** A project without hexagen works as it does today, and its governance checks report `not-configured`.
7. **fleet-v2 never writes hexagen's files.** It never writes `.architecture/` or `.hexagen/` into a project, and never runs `hexagen sync`, `adopt` or `bootstrap` against one except inside a lane whose brief asks for it.

## 3. Detecting a hexagen project (the probe)

**Marker.** The identity lives in the `generator` block that hexagen's loader reads: the manifest, or the side-car `.architecture/generator.config.yaml` when hexagen has moved `generator` there. hexagen's H3 names exactly where.
- **New in the contract (H1):** `generator.name: "@hexagen-monaco/sync"`, alongside the existing `generator.version`, with `schemaVersion` at the root of the manifest.
- **Legacy manifests** without `name` fall back to a `@hexagen-monaco/*` pin in `package.json`.
- `hexagen manifest migrate` adds the name going forward.

**States.** The probe reads these from files only:

| State | Signal | Meaning |
|---|---|---|
| `provisioned` | `generator.name` is hexagen's; `schemaVersion` is an integer | Governed; joins the fan-out set at its version |
| `provisioned-legacy` | A manifest without `name`, plus a hexagen pin in `package.json` | Governed; its next update adds the name |
| `adopting` | `.architecture/layout.yaml` or `.hexagen/` present, no manifest | Brownfield adoption is underway; no contract checks yet |
| `none` | None of the above | Not governed; works as today |

**Never run project code.** The probe reads YAML and JSON only. It never executes the project's `node_modules/.bin/hexagen` or anything else from the project: that is code the project supplies.

**Inventory.** The probe records `{ state, generatorVersion, pinnedVersion }` on the project profile. That set decides who gets a fan-out work order.

## 4. The pipeline

| Stage | Owner | What crosses the boundary | fleet-v2 port and adapter |
|---|---|---|---|
| Provision a new project | hexagen | A repository with a manifest and pinned hexagen tooling | None. fleet-v2 registers it with `projects add` |
| Adopt an existing project | **Both, writing to separate places**: hexagen writes `.architecture/` in the repository; fleet-v2 writes a profile in its state directory | Nothing | The probe (F2) reports the hexagen state |
| Architectural governance | hexagen | An exit code plus the JSON findings line | Phase 1: installation verification procedures (F3, no code). Phase 2: `ArchitectureConformancePort` and `HexagenCliAdapter` (F4) |
| Lane dispatch | fleet-v2 | The frozen brief | Existing |
| Gate | fleet-v2 | Gate commands from the profile's `gateProcedures` | The acceptance gate (planned S2) gains the hexagen checks as predicates (F5) |
| Evidence and acceptance | fleet-v2 | The findings line attached to the head-bound `VerificationReceipt` | Existing receipt port, with the F4 result |
| Contract updates | hexagen releases; fleet-v2 fans out | The release version and its CHANGELOG entries | The inventory (F2) and update work orders (F6) |

## 6. Decisions

| # | Question | Decision or default |
|---|---|---|
| D1 | Integrate through verification procedures (F3) or a dedicated port (F4)? | **Procedures first.** F4 only when the JSON findings are needed in evidence |
| D2 | Who owns the contract? | **hexagen-monaco** (owner, 2026-10-25). fleet-v2 requests changes as work orders and mirrors the shapes leniently |

## 7. Hard to undo

- **hexagen types in fleet-v2's domain or application layers.** This plan forbids it; adding it later would weld the two together.
- **fleet-v2 writing `.architecture/` or `.hexagen/` into projects.** That would let two owners write one tree.
- **Moving the toolchain pin out of the manifest template** without a hexagen feature to support it.

## 8. Assumptions

- **The contract is the tools:** hexagen keeps its command-line tools, their JSON lines and exit codes as the supported contract (ADR-0056). If hexagen moved to a library API, F4's adapter would change, but nothing past the port would.
- **Projects are on the npm path:** every provisioned project consumes hexagen through `package.json`. A project using a different package manager needs F2's legacy signal extended.

## Challenge this

F6 makes fleet-v2 the place where hexagen updates are proposed for every project, which pushes fleet-v2 toward being hexagen's update service. The alternative is a hexagen command, `hexagen outdated`, run in each project, with fleet-v2 only dispatching what it reports. That keeps hexagen's knowledge in hexagen but needs the probe to run project code, which §3 forbids. Is the file-read inventory the right line?
